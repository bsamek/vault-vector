Vault Vector — Architecture

Semantic search for Obsidian, with two interchangeable embedding backends.

The two modes at a glance

Atlas auto-embeddefault

MongoDB Atlas owns the embeddings. The plugin pushes raw note content; Atlas calls Voyage under the hood, stores vectors in its Vector Search index, and runs $vectorSearch server-side.

  • No API keys in the plugin
  • Server-side ANN search (scales)
  • Requires an Atlas cluster

Voyage direct (local)

The plugin calls Voyage AI itself with your API key, stores embeddings in a local JSON cache, and ranks results by brute-force cosine similarity in-process.

  • No cluster to host
  • Full control over model and input type
  • Brute-force; best for ≤ a few thousand notes

Sync flow

In Atlas mode, the plugin never sees a vector. In Voyage mode, the plugin holds them and persists them next to the plugin code.

Search flow

Voyage mode uses input_type=query for the lookup vector (vs. document at sync time). This matches Voyage's recommended asymmetric retrieval setup.

Reranking (optional)

Reranking is a search-time post-processing step that applies to both modes. When enabled, the backend pulls 5× resultLimit candidates (capped at 50) instead of resultLimit, then Voyage's /v1/rerank endpoint does joint query-document attention and returns a reordered list. The plugin replaces each hit's similarity score with the reranker's relevance_score and trims back to resultLimit.

  • Why over-fetch? Most of the gain comes from promoting candidates the embedding model ranked 11-50 into the top slots. Reranking only the top-K would waste the call.
  • Why both modes? Atlas auto-embed returns vector-ranked hits with content; the plugin can hand them straight to the reranker. Voyage-local does the same with locally cached content. The reranker path is identical past the candidate pull.
  • Instructions are not a separate API parameter; if set, the plugin prepends the trimmed instruction to the query as ${instruction}\n\n${query} before calling rerank.
  • API key is reused from the Voyage-direct field. Reranking always calls Voyage, even in Atlas mode, so settings shows an inline warning when the toggle is on without a key, and the Search command aborts with a Notice if the user invokes it that way.
  • Failure handling lives in main.ts: applyRerank throws on HTTP errors; the search closure catches, fires a Notice, and falls back to vector-ordered results. This keeps search.ts free of Obsidian imports.

Local cache format

In Voyage mode the cache lives at <vault>/.obsidian/plugins/vault-vector/embeddings.json:

{
  "version": 1,
  "model": "voyage-4",
  "entries": {
    "notes/topic.md": {
      "mtime": 1715000000000,
      "embedding": [0.012, -0.034, ...],
      "content": "Full note text..."
    }
  }
}

On load, if the cached model doesn't match settings, the whole cache is discarded and the next sync re-embeds everything. The diff against the vault uses path + mtime: anything new or modified gets re-embedded; anything missing from the vault gets removed.

Why JSON? Vaults of a few thousand notes fit comfortably (≈80 MB at the upper end). If that ever becomes painful, a base64'd Float32Array format is the obvious next step.

Code map

  • src/main.ts — plugin entry, dispatches sync/search by provider
  • src/settings.ts — settings schema, defaults, and Obsidian settings UI
  • src/atlas.ts — lazy Atlas client + collection factory
  • src/sync.ts — runSync (Atlas) and runLocalSync (Voyage)
  • src/auto-sync.ts — vault-event watcher with debounce, size/age caps, backoff retry, and sweep timer
  • src/search.ts — executeSearch, executeLocalSearch, applyRerank, candidateCount, and the suggest modal
  • src/voyage.ts — Voyage REST client with batching, plus createVoyageReranker for /v1/rerank
  • src/local-store.ts — JSON-backed embedding cache with diff/upsert/remove
  • src/local-search.ts — cosine similarity + top-K ranking

What's deliberately out of scope

  • No native modules or ANN index for local mode (revisit at ~10K+ notes).
  • No binary cache format yet.
  • No Voyage rate-limit, retry, or backoff handling. Errors surface; re-run sync.
  • Auto-sync works for both modes but does a full re-sync on each flush rather than a targeted per-file operation; this is fine up to a few thousand notes but may feel slow on very large vaults.
